# 1. PRIMARY MISSION

Transform the existing YouTube Clipping Intelligence application into a polished, reliable, production-ready platform.

This is not a simple UI review.

You are responsible for auditing, repairing, integrating, and validating the entire application across all seven primary sidebar sections.

Every page must satisfy four requirements:

1. **Visual Excellence:** Premium, cohesive, professional light-theme interface.
2. **Functional Integrity:** Every button, control, interaction, modal, slider, and workflow must work.
3. **Backend Integrity:** Every operation must communicate with the correct real backend service.
4. **Engineering Reliability:** No broken routes, runtime errors, silent failures, mock implementations, or regressions.

You must inspect the existing codebase before making assumptions.

Do not rebuild functioning systems unnecessarily. Preserve working architecture, improve weak implementations, and repair actual defects.

Your objective is to leave the repository in a demonstrably better state than you found it.

# 4. SHARED DESIGN SYSTEM & VISUAL QUALITY CONTRACT

All seven agents must follow one consistent design language.

The application must feel like one carefully designed product rather than seven independently developed pages.

## Theme

**Light theme is the primary design direction.**

Requirements:

- Consistent light surfaces.
- Sophisticated neutral backgrounds.
- Clear typography hierarchy.
- Restrained use of blue accent colors.
- Subtle borders and shadows.
- Consistent corner radii.
- Professional iconography.
- Clear visual grouping.
- High-contrast interactive controls.
- Consistent loading, empty, success, and error states.

Avoid:

- Unnecessary gradients.
- Excessive glassmorphism.
- Random colored cards.
- Overly rounded components.
- Excessive borders.
- Dark patches inside light-theme layouts.
- Generic AI-generated dashboard aesthetics.
- Decorative elements without functional purpose.

Video viewports can remain black.

The surrounding interface must respect the light-theme design system.

## Shared component consistency

All agents must reuse existing shared components and tokens wherever possible.

Before introducing a new component:

1. Search for an existing equivalent.
2. Check whether it can be extended.
3. Avoid duplicate implementations.
4. Preserve existing shared component contracts.

## Interaction quality

Every interactive control must have:

- A clear purpose.
- A visible interaction state.
- Correct disabled states.
- Loading feedback when appropriate.
- Success feedback.
- Useful error feedback.
- Keyboard accessibility where applicable.

No decorative controls pretending to be functional.

# 5. ZERO-MOCK AND DATA INTEGRITY POLICY

This is a strict requirement.

Do not introduce fake functionality to make the UI appear complete.

Prohibited:

- Hardcoded fake project records.
- Fake trending videos.
- Dummy transcript sentences.
- Artificially generated waveform data presented as actual audio.
- Fake GPU utilization.
- Simulated publishing success.
- Hardcoded successful API responses.
- Mock fallback data in production paths.

If the backend does not provide a capability:

1. Identify the missing backend functionality.
2. Inspect whether an existing service can provide it.
3. Implement the missing functionality if it is within scope.
4. Otherwise expose an honest unavailable state.
5. Document the limitation.

Test fixtures and mocks are permitted in isolated automated tests, but must never silently become production data.

# 6. MULTI-AGENT COORDINATION PROTOCOL

Parallel execution is mandatory, but uncontrolled parallel editing is prohibited.

## Phase A — Initial reconnaissance

Before implementation:

1. Inspect repository structure.
2. Identify frontend routing.
3. Identify shared components.
4. Inspect backend routes.
5. Inspect database models.
6. Identify state-management architecture.
7. Identify API client conventions.
8. Identify existing tests.
9. Identify build and development commands.

The orchestrator creates a shared architecture map.

## Phase B — Parallel independent audits

Spawn all seven tab agents.

Each agent must initially inspect its assigned section and report:

- Existing implementation.
- Broken functionality.
- Missing functionality.
- UI/UX problems.
- API mismatches.
- State-management issues.
- Security concerns.
- Test coverage gaps.
- Dependencies on other sections.

Do not immediately start seven uncontrolled rewrites.

Establish findings first.

## Phase C — Parallel remediation

Once initial findings are available, agents can work concurrently.

Rules:

- Each agent owns its assigned route and components.
- Shared files require orchestrator approval.
- Do not overwrite another agent's changes.
- Do not modify shared API contracts independently.
- Communicate dependencies immediately.
- Preserve existing working functionality.
- Run focused tests after meaningful changes.

If two agents need the same shared component, the orchestrator assigns ownership to one agent and communicates the resulting interface to the other.

## Phase D — Integration checkpoints

The orchestrator must review progress at meaningful milestones.

Required checkpoints:

1. Architecture and findings completed.
2. All seven initial audits completed.
3. Primary UI remediation completed.
4. Backend integration completed.
5. Focused tests completed.
6. Cross-tab integration completed.
7. Final system verification completed.

An agent cannot declare completion without reporting its changed files, tests, and verification evidence.

# 9. FAILURE MANAGEMENT

When an agent encounters a blocker:

1. Record it in `AUDIT_PROGRESS.md`.
2. Identify the actual root cause.
3. Determine whether another agent owns the dependency.
4. Notify the orchestrator.
5. Agree on a resolution.
6. Implement the fix.
7. Re-run affected tests.

Do not silently skip failing tests.

Do not hide errors with broad exception handlers.

Do not disable linting or type checks to obtain a successful build.

Do not weaken existing security checks to make an integration work.

If a third-party API is unavailable due to credentials, quotas, permissions, or service outages, distinguish that from an application defect.
